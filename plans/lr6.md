# [ОПЦИОНАЛЬНО] ЛР №6. Веб-интерфейс на серверном рендеринге (Jinja2)

> **Вся лаба дополнительная.** В ТЗ (ЛР0) веб-интерфейс сейчас отнесён к «вне рамок». Если делаете эту лабу, уберите веб-интерфейс из этого списка в ТЗ и добавьте его в раздел «Архитектура».

**Ветка:** `lr6-jinja` · **Технологии:** Jinja2 (`fastapi.templating.Jinja2Templates`), формы (python-multipart), немного JS только для WebSocket
**Зависит от:** ЛР2 (сервисный слой, JWT), ЛР3 (`RagClient`), ЛР4 (Notification Service), ЛР5 (compose)
**Отчёт:** `docs/reports/lr6.md` (шаблон `docs/reports/_template.md`) · **Подготовка к сдаче:** `defense/lr6.md` + `defense/lr6-cheatsheet.md` (составляет Claude Code, раздел 8)

## 1. Задание из методички

Дополнить систему HTML-интерфейсом на шаблонизаторе Jinja2. Веб-интерфейс:

- [ ] позволяет выполнять основные операции предметной области через браузер (отправлять запросы и видеть результаты);
- [ ] построен на основе уже существующего REST API;
- [ ] использует существующую бизнес-логику приложения;
- [ ] в шаблонах только логика представления: вывод данных, циклы, условия, наследование. Бизнес-логики и обращений к БД в шаблонах нет;
- [ ] HTML-представления и маршруты для основных сценариев: главная, список объектов, карточка, создание, редактирование;
- [ ] новый функционал — часть **API Service**. Новых сервисов и контейнеров нет, отдельного фронтенд-сервиса нет, бизнес-логика не дублируется. Все действия пользователя обрабатывает существующий сервисный слой.

**Сдача:** демонстрация работы приложения.

## 2. Результат лабы

Веб-маршруты `/web/*` внутри API Service. Они вызывают те же сервисы (`IssueService`, `ArticleService`, `OcrService`, `RagClient` и т. д.), что и REST-роутеры — через `Depends`, без HTTP-запросов к самим себе.

## 3. Структура файлов

```
services/api/src/corag_api/
  web/
    __init__.py  router.py              # APIRouter(prefix="/web", include_in_schema=False)
    auth.py                             # логин-форма → JWT в HttpOnly cookie; get_current_user_web (cookie → тот же decode_token)
    forms.py                            # разбор форм в существующие DTO (ArticleCreate и т. п.), ошибки валидации → форма с сообщениями
    flash.py                            # flash-сообщения через подписанную cookie
  templates/
    base.html                           # шапка, меню по роли, flash, {% block content %}
    macros/forms.html  macros/pagination.html  macros/citations.html
    index.html                          # главная: форма вопроса к архиву + последние выпуски
    login.html  register.html
    ask_result.html                     # ответ + источники со ссылками на статьи и страницы
    issues/list.html  issues/detail.html  issues/form.html  issues/upload.html
    articles/list.html  articles/detail.html  articles/form.html
    pages/detail.html                   # текст страницы (Markdown → HTML)
    admin/users.html  admin/ocr_job.html  # прогресс OCR в реальном времени
  static/
    style.css                           # небольшой собственный CSS или classless-фреймворк из локального файла
    ws.js                               # ~40 строк: подключение к /ws, обновление прогресса и списка событий
```

## 4. Шаги реализации

### Шаг 1. Подключение шаблонов

- `Jinja2Templates(directory=...)`, `app.mount("/static", StaticFiles(...))`.
- Глобальные переменные шаблонов: `current_user`, `request`.
- Фильтр `markdown` — рендер текста страниц (пакет `markdown` или `markdown-it-py`) с экранированием HTML.

### Шаг 2. Аутентификация в браузере

- `GET/POST /web/login`:
    - `AuthService.authenticate`;
    - JWT записывается в cookie `access_token` (`HttpOnly`, `SameSite=Lax`, `Max-Age` = TTL токена);
    - редирект на `/web/`.
- `POST /web/logout` удаляет cookie. `GET/POST /web/register` — регистрация.
- `get_current_user_web` читает токен из cookie и использует тот же `decode_token`. Нет токена → редирект на `/web/login`. Чужая роль → страница 403.
- Без JWT (если в ЛР2 он не делался): подписанная сессионная cookie (`itsdangerous`) с `user_id`.

### Шаг 3. Страницы и маршруты

| Маршрут | Роль | Что делает (через какой сервис) |
| --- | --- | --- |
| `GET /web/` | researcher+ | Главная: форма вопроса, последние выпуски (`IssueService.list`) |
| `POST /web/ask` | researcher+ | `RagClient.ask` → `ask_result.html`, источники ведут на статьи и страницы |
| `GET /web/issues`, `GET /web/issues/{id}` | researcher+ | Список с фильтром по году; карточка: страницы, статьи, статус |
| `GET/POST /web/issues/new`, `/web/issues/{id}/edit` | admin | Создание и редактирование (`IssueService`) |
| `GET/POST /web/issues/{id}/upload` | admin | Загрузка PDF (`IssueService.upload_scan`) |
| `POST /web/issues/{id}/ocr` | admin | `OcrService.start` → редирект на страницу задачи |
| `GET /web/ocr-jobs/{id}` | admin | Прогресс OCR: начальное состояние из БД, дальше обновления через `ws.js` |
| `GET /web/articles`, `GET /web/articles/{id}` | researcher+ | Каталог с фильтрами (автор, ключевое слово, год); карточка статьи с текстом страниц |
| `GET/POST /web/articles/new`, `/web/articles/{id}/edit`, `POST /web/articles/{id}/delete` | admin | Форма: выпуск, страницы, мультивыбор авторов (порядок), ключевые слова через запятую |
| `GET /web/issues/{id}/pages/{n}` | researcher+ | Текст страницы в виде HTML |
| `GET /web/admin/users`, `POST /web/admin/users/{id}` | admin | Роль и блокировка (`UserService`) |

Паттерн POST → redirect → GET (303), чтобы обновление страницы не отправляло форму повторно. Ошибки домена (409, 422) снова показывают форму с сообщением и введёнными значениями.

### Шаг 4. Прогресс OCR в браузере

- `ws.js` подключается к `/ws` (через Nginx того же origin или напрямую к порту Notification Service).
    - Токен для query берётся из небольшого эндпоинта `GET /web/ws-token`: тот же JWT, отдаётся только авторизованному пользователю. Сама cookie `HttpOnly` и недоступна JS.
- `ocr.progress` обновляет `<progress>`; `ocr.completed`, `issue.indexed` и `ocr.failed` выводятся строками в ленте событий.
- JS здесь только транспорт для уведомлений. Бизнес-логики в нём нет.

### Шаг 5. Шаблоны: правила

- Наследование `{% extends "base.html" %}`, макросы для полей форм, пагинации и списка источников.
- В шаблоны передаются готовые DTO (`ArticleOut` и т. п.), а не ORM-объекты. Запросов к БД и вызовов сервисов из шаблонов нет.
- Автоэкранирование включено. Markdown страниц рендерится фильтром с санитизацией.

### Шаг 6. Тесты

- `TestClient`:
    - без cookie → редирект на логин;
    - логин ставит cookie;
    - researcher получает 403 на `/web/issues/new`;
    - создание статьи через форму → редирект и запись в БД;
    - `/web/ask` с подменённым `RagClient` (в тестах) показывает источники.
- Проверка «тонких» шаблонов: grep по `templates/` не находит обращений к сессии или репозиториям.

## 5. Как проверить и показать

```bash
docker compose up --build -d
open http://localhost/web/        # через Nginx, или http://localhost:8000/web/
```

Сценарий:

1. Войти как исследователь → задать вопрос → перейти по источнику к статье и странице.
2. Войти как админ → создать выпуск → загрузить скан → запустить OCR → смотреть прогресс → после `issue.indexed` найти текст нового выпуска через вопрос.

## 7. Подводные камни

- Нельзя вызывать REST-эндпоинты через `httpx` из веб-роутов: это дублирование, его прямо запрещает методичка. Вызывать сервисы.
- Формы с мультивыбором: `request.form()` → `getlist("author_ids")`.
- CSRF: при `SameSite=Lax` и POST-формах только с того же origin риск минимален. Это стоит упомянуть на защите.
