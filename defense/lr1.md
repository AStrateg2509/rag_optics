## 2. Минимальная теория

### 2.1. Реляционная модель и нормализация

Данные хранятся в таблицах-отношениях; строку однозначно определяет **первичный ключ** (`issues.id`), ссылки на другие таблицы — **внешние ключи** (`pages.issue_id → issues.id`). Связь **1:N** — внешний ключ на стороне «многих»: у выпуска много страниц, статей и задач OCR. Связь **M:N** нельзя выразить одним FK, нужна **таблица-связка** с составным PK: `article_keywords(article_id, keyword_id)`. Если у самой связи есть атрибут, связка становится полноценной сущностью: `article_authors.author_order` — порядок автора в статье.

Схема CO-RAG приведена к **3НФ**: значения атомарны (1НФ — ключевые слова не хранятся строкой через запятую, а лежат в `keywords`); неключевые поля зависят от всего ключа (2НФ — `author_order` зависит от пары статья+автор, а ФИО автора вынесено в `authors`); нет транзитивных зависимостей (3НФ — год и номер выпуска не дублируются в статьях, их получают JOIN-ом через `issue_id`). Сознательное решение: статья связана со страницами **диапазоном** `page_start..page_end`, а не FK. Индексация страниц не ждёт разметки статей, а исправление диапазона не требует переиндексации.

### 2.2. Транзакции и ACID

Транзакция — группа операций, которая выполняется целиком или не выполняется вовсе. **A**tomicity — всё или ничего (сценарий демо откатывается одним `rollback`). **C**onsistency — после транзакции выполнены все ограничения: CHECK `page_start <= page_end`, FK, UNIQUE. **I**solation — параллельные транзакции не видят незафиксированных изменений друг друга. **D**urability — зафиксированное переживает сбой (WAL).

В PostgreSQL уровень изоляции по умолчанию — **READ COMMITTED** (проверено: `SHOW default_transaction_isolation` → `read committed`): каждый оператор видит данные, зафиксированные к моменту *его* начала. Поэтому «проверить SELECT-ом, что активной задачи нет, а потом вставить» — гонка: две транзакции могут одновременно увидеть «нет». В CO-RAG правило «одна активная задача OCR на выпуск» обеспечивает **частичный уникальный индекс** `ux_ocr_jobs_active … WHERE status IN ('queued','running')`: второй INSERT получит ошибку уникальности, которую репозиторий превращает в `Conflict` (→ HTTP 409 в ЛР2).

**SAVEPOINT** — точка отката внутри транзакции. `OcrJobRepository.create_active` вставляет задачу в `begin_nested()`: при конфликте откатывается только вставка, а внешняя транзакция вызывающего кода остаётся рабочей.

### 2.3. ORM: Data Mapper, Unit of Work, Identity Map

**ORM** отображает строки таблиц на объекты. Есть два паттерна. В **Active Record** (Django ORM) объект сам себя сохраняет: `user.save()`. В **Data Mapper** (SQLAlchemy) модель — обычный класс, а сохранением занимается отдельный посредник, `Session`. Поэтому модели не зависят от подключения, и их легко тестировать.

`Session` реализует два паттерна:

- **Unit of Work** — копит изменения объектов (new/dirty/deleted) и при `flush()` отправляет их в БД одним пакетом в правильном порядке (сначала `issues`, потом `pages`). При `commit()` транзакция фиксируется.
- **Identity Map** — в рамках сессии одной строке соответствует один объект: два `session.get(Issue, 1)` вернут один и тот же экземпляр.

Ниже по уровню: **Engine** — фабрика соединений с **пулом** (соединения переиспользуются, а не открываются на каждый запрос); `async_sessionmaker` — фабрика сессий с общими настройками (`session.py` → `create_sessionmaker`). В CO-RAG репозитории **не коммитят**: границы транзакции задаёт вызывающий (`get_session()` коммитит при успехе и откатывает при исключении). Тогда одна бизнес-операция из нескольких репозиториев атомарна.

### 2.4. Загрузка связей и проблема N+1

По умолчанию связь (`article.authors_assoc`) загружается **лениво** (lazy): при первом обращении — отдельным SELECT. Если вывести каталог из 50 статей с авторами, получится 1 запрос статей + 50 запросов авторов. Это и есть **N+1**. Решения:

- `selectinload` — второй запрос `… WHERE article_id IN (…)` для всех статей сразу (хорош для коллекций);
- `joinedload` — JOIN в том же запросе (хорош для many-to-one: статья → выпуск);
- `contains_eager` — связь заполняется из JOIN, который уже есть в запросе (используется в `ArticleRepository.filter`, где `issues` присоединён ради фильтра по году).

В асинхронном коде ленивая загрузка вообще недопустима: неявный SELECT при обращении к атрибуту не может выполниться без `await`, и SQLAlchemy бросает `MissingGreenlet`. Поэтому в CO-RAG связи грузятся явно (`_RELATIONS` в `repositories/articles.py`), а сессии создаются с `expire_on_commit=False`: иначе после `commit` все атрибуты «протухают», и следующее обращение тоже вызывает загрузку.

### 2.5. Асинхронный доступ к БД

Сервисы CO-RAG (FastAPI, gRPC `grpc.aio`) работают в одном потоке на event loop. Синхронный драйвер блокировал бы весь цикл, пока ждёт ответ БД. Асинхронный драйвер **asyncpg** отдаёт управление циклу (`await`), и в это время обслуживаются другие запросы. SQLAlchemy 2.0 даёт `create_async_engine` и `AsyncSession`. Ограничение: **одна `AsyncSession` — одна корутина**. Сессия хранит состояние одной транзакции на одном соединении. Параллельные `flush` через `asyncio.gather` над одной сессией падают с `InvalidRequestError: Session is already flushing` и `IllegalStateChangeError` (проверено на CO-RAG), а простые `execute` выполняются по очереди, то есть параллелизма всё равно нет. Для параллельных запросов нужны отдельные сессии.

### 2.6. Индексы: B-tree и HNSW

**B-tree** — сбалансированное дерево по упорядоченным значениям, ускоряет `=`, `<`, `BETWEEN`, `ORDER BY`. Примеры в CO-RAG: составной `ix_articles_issue_pages (issue_id, page_start, page_end)` — под JOIN «страница внутри диапазона статьи»; индексы под каждым UNIQUE. **Частичный индекс** строится только по строкам, удовлетворяющим `WHERE`, — так задано правило «одна активная задача».

Поиск ближайших векторов «в лоб» — полный перебор с расчётом расстояния до каждого (Seq Scan + Sort). **pgvector** добавляет тип `vector(n)`, операторы расстояния (`<=>` — косинусное, `<->` — L2, `<#>` — минус скалярное произведение) и приближённые индексы (ANN). **HNSW** (Hierarchical Navigable Small World) — многослойный граф: на верхних слоях мало вершин и «длинные» рёбра, на нижнем — все векторы. Поиск жадно спускается сверху вниз, на каждом слое переходя к ближайшему соседу. Параметры: `m` — число связей вершины (16), `ef_construction` — ширина поиска при построении (64), `hnsw.ef_search` — при запросе (по умолчанию 40). Результат **приближённый**: возможен пропуск истинного соседа, зато поиск быстрый. Альтернатива **IVFFlat** делит векторы на кластеры (k-means) и ищет в нескольких ближайших. Его надо строить на уже загруженных данных, и полнота поиска у него хуже при той же скорости. HNSW строится медленнее и занимает больше памяти, но работает и на пустой таблице. Поэтому индекс `ix_chunks_embedding` создаётся сразу в миграции. На 40 строках сида планировщик честно выбирает Seq Scan (проверено `EXPLAIN`), а при `SET enable_seqscan = off` — `Index Scan using ix_chunks_embedding`.

### 2.7. Миграции (доп. задание)

Миграция — версионированный скрипт изменения схемы с парой `upgrade()`/`downgrade()`. **Alembic** хранит текущую версию в таблице `alembic_version` и выстраивает ревизии в цепочку (`<base> → 0001 → 0002`). **Autogenerate** сравнивает `Base.metadata` с реальной БД и генерирует черновик. Его обязательно надо вычитать: autogenerate не создаёт расширения (`CREATE EXTENSION vector` добавлен вручную), не удаляет ENUM-типы в `downgrade` (добавлено вручную) и не видит переименования (вместо rename получится drop + add с потерей данных). `naming_convention` даёт constraint'ам стабильные имена, без них `downgrade` не сможет удалить constraint по имени.

## 3. Вопросы преподавателя с ответами

1. **Зачем ORM, если можно писать SQL?**
   ORM избавляет от ручного маппинга строк в объекты и SQL для типовых CRUD, следит за порядком операций (Unit of Work) и даёт типизированные запросы. Сложные запросы в CO-RAG всё равно пишутся явно, но через построитель SQLAlchemy Core: `ChunkRepository.nearest` повторяет SQL из раздела 5.3 ТЗ. ORM не отменяет знание SQL — надо понимать, какие запросы он генерирует (`ECHO_SQL=true`).

2. **Что такое Session? Unit of Work и Identity Map.**
   `Session` — единица работы: копит изменения объектов и при `flush` отправляет их в БД, при `commit` фиксирует транзакцию. Identity Map гарантирует один объект на строку в пределах сессии. В CO-RAG сессия создаётся в `session.py` → `get_session()`.

3. **Кто управляет транзакцией — commit и rollback?**
   Вызывающий код, а не репозиторий: методы `BaseRepository` делают только `flush` (`repositories/base.py`). Так одна операция из нескольких репозиториев атомарна: например, `create_with_relations` создаёт статью, ключевые слова и связки в одной транзакции. `get_session()` коммитит при успехе и откатывает при исключении.

4. **Как реализована M:N и зачем association object?**
   Статья↔ключевое слово — простая таблица `article_keywords` и `relationship(secondary=…)`. У связи статья↔автор есть своё поле `author_order`, поэтому она оформлена моделью `ArticleAuthor` с составным PK. `Article.authors_assoc` упорядочен по `author_order`, удобное свойство `Article.authors` отдаёт список авторов (`models.py`).

5. **Что такое ленивая загрузка и проблема N+1? Как решаете?**
   Ленивая связь подгружается отдельным SELECT при первом обращении. В цикле по N объектам это N лишних запросов. В `ArticleRepository.filter` авторы и ключевые слова грузятся `selectinload` (2 доп. запроса на всю страницу каталога), выпуск — `contains_eager` из уже сделанного JOIN.

6. **Что такое `MissingGreenlet` и как его избежать?**
   Ошибка возникает, когда в async-коде SQLAlchemy пытается сделать неявный (ленивый) запрос без `await`. Избегаем двумя способами: явной загрузкой связей и `expire_on_commit=False` в `create_sessionmaker` (иначе после commit атрибуты истекают и перечитываются). Для server default полей SQLAlchemy 2.0 получает значения через `RETURNING`.

7. **`ON DELETE CASCADE` в БД против `cascade` в ORM?**
   `ON DELETE CASCADE` удаляет дочерние строки сама БД — одним оператором, работает и для SQL мимо ORM. ORM-каскад (`cascade="all, delete-orphan"`) сначала загружает детей и удаляет каждого отдельно. Для `Issue → pages/articles/ocr_jobs` использован каскад БД плюс `passive_deletes=True` (ORM не грузит детей). ORM-каскад оставлен для `authors_assoc`, где связки меняются из Python (`Article.set_authors`).

8. **Что такое ACID? Какой уровень изоляции у PostgreSQL по умолчанию?**
   Атомарность, согласованность, изолированность, долговечность (см. 2.2). По умолчанию — READ COMMITTED: каждый оператор видит данные, зафиксированные до его начала. Поэтому проверки «нет ли уже такой строки» делаются ограничениями БД, а не SELECT перед INSERT.

9. **В какой нормальной форме схема?**
   В 3НФ: атомарные значения, ключевые слова и авторы вынесены в справочники, связи — в таблицы-связки, а данные выпуска не дублируются в статьях. Единственное «нереляционное» место — связь статья↔страницы через диапазон. Это сознательное решение, чтобы индексация не зависела от разметки статей.

10. **Зачем pgvector? HNSW против IVFFlat.**
    pgvector хранит эмбеддинги прямо в PostgreSQL, рядом с метаданными: один запрос и находит ближайшие фрагменты, и JOIN-ит выпуск и статью (`nearest`). HNSW — графовый приближённый индекс: лучше соотношение скорость/полнота, строится на пустой таблице, но дороже по памяти и времени построения. IVFFlat требует данных для кластеризации.

11. **Что такое частичный уникальный индекс и зачем он здесь?**
    Индекс строится только по строкам из `WHERE`: `ux_ocr_jobs_active` уникален по `issue_id` среди задач `queued/running`. Завершённых задач на выпуск может быть сколько угодно, активная — одна. Нарушение даёт `IntegrityError`, `OcrJobRepository.create_active` превращает его в `Conflict` (демо, сценарий 7).

12. **Как работает `INSERT … ON CONFLICT` и где применяется?**
    Если вставка нарушает уникальность по указанным колонкам, вместо ошибки выполняется `DO UPDATE` (или `DO NOTHING`) атомарно, без гонки «SELECT, потом INSERT». `PageRepository.upsert` обновляет текст страницы по ключу `(issue_id, page_number)` — повторный OCR не создаёт дубль. `KeywordRepository.get_or_create_many` использует `DO NOTHING`.

13. **Почему одну `AsyncSession` нельзя использовать в параллельных корутинах?**
    Сессия хранит состояние одной транзакции на одном соединении. Параллельные `flush` над ней SQLAlchemy запрещает: `InvalidRequestError: Session is already flushing`, затем `IllegalStateChangeError` (проверено). Для параллелизма — отдельная сессия на задачу. В API (ЛР2) это будет сессия на запрос через `Depends`.

14. **Как устроены тесты и почему они не мешают друг другу?**
    Отдельная БД `corag_test`, схема создаётся один раз за прогон (`create_schema`). Каждый тест работает внутри внешней транзакции, которая в конце откатывается. `join_transaction_mode="create_savepoint"` превращает commit/rollback кода под тестом в SAVEPOINT (`tests/db/conftest.py` → `session`).

15. **[Доп.] Что делает Alembic и в чём ограничения autogenerate?**
    Alembic применяет версионированные миграции и хранит текущую версию в `alembic_version`. Autogenerate сравнивает модели с БД. Он не видит переименований, не создаёт расширения и не удаляет ENUM-типы в `downgrade`: в `0001_initial_schema.py` это дописано вручную. `alembic check` подтверждает, что модели и миграции синхронны.
